## 1. Предметная область

Портал ДОТ РосНОУ (dst.rosnou.ru) — система дистанционного обучения, в которой студенты, преподаватели и администраторы взаимодействуют в рамках учебного процесса.

**Основные сущности:**
- **Студент** — обучающийся с ФИО, группой, направлением, email, номером зачётной книжки
- **Преподаватель** — ППС с ФИО, учёной степенью, email
- **Дисциплина** — учебный курс с названием, преподавателем, семестром, часами
- **Оценка** — результат аттестации студента по дисциплине
- **Долг** — академическая задолженность (экзамен/зачёт/курсовая)
- **Пересдача** — окно для повторной сдачи с датой, аудиторией, лимитом студентов

**Ключевые процессы:**
- Просмотр студентом своих дисциплин, оценок, долгов
- Запись студента на пересдачу
- Выставление преподавателем оценок
- Создание преподавателем окна пересдачи
- Администрирование справочников (студенты, преподаватели)
- Аналитика успеваемости для системного аналитика

## 2. Матрица стейкхолдеров и прав доступа (Ролевая модель)

| Функция системы | Студент | Преподаватель | Администратор | Системный аналитик |
|---|---|---|---|---|
| Просмотр своих дисциплин | Да | Нет | Нет | Нет |
| Просмотр своих оценок | Да | Нет | Нет | Нет |
| Просмотр своих долгов | Да | Нет | Нет | Нет |
| Запись на пересдачу | Да | Нет | Нет | Нет |
| Просмотр списка всех студентов | Нет | Да | Да | Нет |
| Просмотр списка дисциплин | Нет | Да | Да | Да |
| Просмотр расписания | Нет | Да | Да | Нет |
| Выставление оценки студенту | Нет | Да | Нет | Нет |
| Создание пересдачи | Нет | Да | Нет | Нет |
| Просмотр всех пересдач | Нет | Да | Да | Нет |
| Добавление/удаление студента | Нет | Нет | Да | Нет |
| Добавление/удаление преподавателя | Нет | Нет | Да | Нет |
| Просмотр журнала действий (Event Log) | Нет | Нет | Нет | Да |
| Настройка бизнес-правил / порогов | Нет | Нет | Нет | Да |

**Архитектурное противоречие:** Преподавателю необходима тяжёлая аналитика успеваемости (динамика оценок, % должников, статистика пересдач), а студенту — мгновенная загрузка своих оценок и запись на пересдачу. Если генерировать аналитические отчёты в той же БД, где студент смотрит оценки, система упадёт в момент сессии.

**Решение (CQRS):** разделить систему на два контура:
- **Транзакционный (OLTP)** — быстрые операции: оценки, долги, записи на пересдачи
- **Аналитический (OLAP)** — отдельное хранилище для отчётов и статистики, синхронизация через очередь сообщений

## 3. Функциональные требования (FR)

### Модуль А: Справочники и конфигурация (Input Configuration Module)

- **FR-01 (Управление студентами):** Система должна предоставлять Администратору интерфейс для добавления и удаления студентов с полями: ФИО, группа, направление, email, номер зачётной книжки.
- **FR-02 (Управление преподавателями):** Система должна позволять Администратору добавлять и удалять преподавателей с указанием ФИО, учёной степени и email.
- **FR-03 (Управление дисциплинами):** Система должна обеспечивать ведение справочника дисциплин с привязкой к преподавателю, семестру и количеству часов.
- **FR-04 (Сохранение шаблонов расписания):** Система должна обеспечивать сохранение расписания занятий по группам (JSON/YAML) для повторного использования в следующих семестрах.

### Модуль Б: Учебный процесс и транзакции (Academic Core Engine)

- **FR-05 (Просмотр своих данных студентом):** Система должна предоставлять Студенту интерфейс для просмотра своих дисциплин, оценок и академических задолженностей — только по своей учётной записи.
- **FR-06 (Выставление оценки):** Система должна позволять Преподавателю выставлять оценку студенту с указанием дисциплины, значения (5/4/3/2/зачёт/незачёт), даты и комментария.
- **FR-07 (Защита от двойной записи — Race Conditions):** Система должна гарантировать блокировку места на пересдаче в момент записи студента, исключая одновременную запись одного и того же студента двумя сессиями.
- **FR-08 (Идемпотентность записи):** Система должна требовать передачи уникального ключа идемпотентности (Idempotency-Key) при записи на пересдачу для предотвращения дублирующих записей при повторном нажатии кнопки.

### Модуль В: Пересдачи и аналитика (Retake & Analytics Module)

- **FR-09 (Создание окна пересдачи):** Система должна позволять Преподавателю создавать окно пересдачи с указанием дисциплины, даты, аудитории, максимального числа студентов и статуса (open/closed).
- **FR-10 (Алгоритм закрытия долга):** Система должна автоматически закрывать академическую задолженность при выставлении положительной оценки (3 и выше) согласно настройкам Системного аналитика.
- **FR-11 (Экспорт отчётности):** Система должна формировать сводные таблицы по успеваемости и обеспечивать выгрузку «сырых» данных о сессиях, оценках и пересдачах во внешние системы (Excel/CSV).

## 4. Нефункциональные требования (NFR) на базе ISO 25010

**Бизнес-контекст:** «Во время сессии 5000 студентов одновременно проверяют оценки и записываются на пересдачи».

| Категория ISO 25010 | Контекст предметной области | Инженерная формулировка требования (NFR) |
|---|---|---|
| **Performance Efficiency** | 5000 студентов одновременно заходят в личный кабинет в день объявления оценок | **NFR-01:** Система должна выдерживать пиковую нагрузку не менее **2000 RPS** на эндпоинт получения своих оценок и не менее **300 RPS** на эндпоинт записи на пересдачу при времени отклика (Latency) p95 не более **200 мс**. |
| **Reliability** | Сбой системы во время сессии ведёт к срыву графика пересдач и апелляций | **NFR-02:** Архитектура должна исключать единую точку отказа (SPOF). Коэффициент доступности (Availability) транзакционного ядра должен составлять **99.9%** (SLA). |
| **Usability** | Студент должен успеть записаться на пересдачу со смартфона в условиях плохой связи | **NFR-03:** Размер передаваемой по сети страницы с оценками для мобильных устройств не должен превышать **200 Кб** в сжатом виде (gzip/brotli). |
| **Maintainability** | Правила закрытия долгов и пороги пересдач могут меняться каждый семестр | **NFR-04:** Модуль бизнес-правил (закрытие долга, лимиты пересдач) должен быть изолирован от логики оценок через паттерн «Стратегия» и покрыт unit-тестами минимум на **70%**. |
| **Security** | Риск накрутки оценок и несанкционированной записи на пересдачу | **NFR-05:** Система должна иметь встроенный механизм Rate Limiting, ограничивающий запросы с одного IP-адреса/аккаунта (не более **10 запросов на запись в минуту**). |

## 5. Системные ограничения и допущения (Constraints)

Формализуем бизнес-рамки первой версии продукта (v1.0), которые нельзя нарушать архитектурно.

- **Constraint-01 (Ограничение по часовому поясу):** Система проектируется в расчёте на работу в пределах одной временной зоны (Москва/MSK). Мультитаймзоновые расписания пересдач и автоматический перевод времени для v1.0 не поддерживаются.
- **Constraint-02 (Ограничение по типам аттестации):** Система v1.0 поддерживает только два типа аттестации: «Экзамен» (exam) и «Зачёт» (credit). Курсовые работы (coursework) как отдельный тип долга не реализуются.
- **Constraint-03 (Технологический стек):** В качестве основного хранилища данных (оценок, долгов, записей на пересдачи) должна использоваться СУБД с поддержкой уровня изолированности транзакций **Serializable** (например, PostgreSQL) для исключения аномалий конкурентного доступа при одновременной записи на одну пересдачу.
- **Constraint-04 (Архитектурный стиль):** Система проектируется как набор независимых микросервисов с единой точкой входа через API Gateway (паттерн Backend-for-Frontend). Монолитная реализация не рассматривается.
- **Constraint-05 (Ограничение по авторизации):** В v1.0 используется упрощённая авторизация без OAuth 2.0 и SSO. Разграничение прав обеспечивается на уровне ролей (student/teacher/admin).
- **Constraint-06 (Ограничение по интеграции с 1С):** Автоматическая синхронизация с учётной системой вуза (1С:Университет) в v1.0 не реализуется — данные вводятся вручную Администратором.
- **Constraint-07 (Ограничение по уведомлениям):** Email- и push-уведомления о новых оценках и пересдачах в v1.0 не реализуются — пользователь видит изменения только при входе в систему.

## 6. Архитектура приложения (микросервисы)

| Сервис | Порт | Назначение |
|--------|------|-----------|
| `students_service` | 5001 | Управление студентами |
| `grades_service` | 5002 | Управление оценками и долгами |
| `retakes_service` | 5003 | Управление пересдачами |
| `api_gateway` | 8000 | Единая точка входа (FastAPI + httpx) |
| `web_app` | 5004 | Веб-интерфейс (Flask + Jinja2) |

**API Gateway** маршрутизирует запросы от Web App к микросервисам, обрабатывает ошибки (503 при недоступности сервиса) и предоставляет endpoint `/health` для мониторинга.

## 7. Запуск проекта

```bash
# 1. Установка зависимостей
pip install -r requirements.txt

# 2. Запуск микросервисов (в отдельных терминалах)
cd students_service && python app.py        # порт 5001
cd grades_service && python app.py          # порт 5002
cd retakes_service && python app.py         # порт 5003

# 3. Запуск API Gateway
cd api_gateway
python -m uvicorn main:app --host 0.0.0.0 --port 8000 --reload

# 4. Запуск Web App
cd web_app && python app.py                 # порт 5004
```

**Проверка:** http://localhost:5004 (GUI) или http://localhost:8000/docs (Swagger).
